# 研究依据与版本边界

## 适用构建

本项目研究对象为 Steam `CL-301524`，存档格式由当前仓库实现支持。已记录的原生主体 `platform/steam/PBZ.exe` SHA-256：

```text
7b4fcd286a350780faf0824d73aa150b21cbf1bccde883e6a96386cbe09973b4
```

本轮检查到的 Steam 安装为 `CL-301524_JKS-17219`，哈希与上方取证对象完全一致。缓存中找到的其他完整原生程序均为同哈希副本；小型 `PBZ.exe` 文件是测试启动器，不是游戏主体。当前偏移派生出的 AES-256 密钥 SHA-256 为 `65b75c306a77eb2df3ed5a7e6b3f8dbef360f6abefa74c465196cfa19af9637c`；工具只保存此指纹，不保存密钥。尚未发现第二个构建或第二种定位算法的认证样本，因此后备路径仅允许已知偏移导出相同指纹的密钥，并要求目标 PBZS GCM 认证通过。

基线 [samples/vanilla-base.sav](../../../samples/vanilla-base.sav) SHA-256：

```text
3782031244b8d71d94e84c18d066d6f5e84ff745c81b4e68567fc87694b3ce37
```

EXE 哈希用于识别精确取证对象；对更新后的未知哈希，密钥指纹可验证已知定位方式是否仍导出同一密钥，目标存档的 GCM tag 再验证该密钥对当前容器是否有效。密钥指纹不匹配时拒绝，不能只靠文件版本字符串、偏移处有数据或可读明文接受。

## 已纠正的高影响误判

**“改 CurrentProfileIdentifierString 就启用了方案”**：旧实现写盘及回读都成功，但真实选择仍由共享设置 `KeyBindingScheme` 控制。验收必须读取那个字段，而不是验证自己刚写的无关字段。

**“GamepadFamilyProfiles 有三条，所以是三种设备/一套共享设置”**：基线三条均为 Xbox，ProfileId 分别对应三个方案。游戏机器码先匹配 Family，再匹配 ProfileId；普通单方案编辑必须保留这一归属。

**“左键攻防”自动意味着保留右键**：只把 Guard 改成 Left 会产生替换效果。保留语义必须显式确保 Right+Left，手柄为 LB+X；这与原指引的闪避冲刺配方分开。

**“有 PBZS 头就应该找 Oodle 解压”**：当前容器已通过 AES-GCM 认证读写确认。旧压缩尝试不是适配其他版本时可直接继承的事实。

## 原生证据入口

详表保存在 `docs/gamepad-profile-evidence.md`，避免在技能中复制整份地址表。核心锚点均为上述构建的首选虚拟地址，ImageBase=`0x140000000`：

- `0x1466edb60`：`SetKeyBindingScheme` 路径，方案枚举经 `0x1468940a0` 转为 profile 字符串后调用引擎 profile 选择。
- `0x146884350`：手柄投影路径；实际读取 Keys 的匹配循环同时检查 Family 和 ProfileId。
- `0x146885710` / `0x1468814c0`：存储更新及清除对应记录的路径，同样保留两个匹配条件。

这些是静态解码证据，不是恢复的官方源代码，也不是游戏输入实测。不要把上述 VA 当作 `ReadKey()` 所用 EXE 文件偏移。

## 后续验证怎样改变结论

读取新存档先做 byte-identical 零修改往返；失败则不支持安全编辑。单方案修改以恢复目标数据后的全文件比较检查范围，包含相同 family 的其他 ProfileId，以及同一 ProfileId 的其他 family。

PBZS 测试必须包含三个合法方案、未知值、篡改 header/nonce/tag/cipher、外部版本变化和 no-op。认证成功且其他 JSON 不变说明生成文件有效；不能代替游戏启动结果。

运行验证需明确记录游戏构建、实际选中方案、物理输入及观察结果。在确认能隔离键位、共享设置和其他本地状态前，不拿真实玩家存档做探针。单独验证“游戏 UI 展示了新绑定”“方案切换采用了对应手柄记录”“同键多动作在实际战斗中生效”，避免将其中一个当成全部成立。
