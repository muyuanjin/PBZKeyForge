# 研究依据与版本边界

## 适用构建

本项目支持 Steam `CL-301524_JKS-17219` 和 1.0302256 / `CL-302256_JKS-17280`，两版证据及验证范围见[游戏版本兼容](../../../docs/game-version-compatibility.md)。首发构建原生主体 `platform/steam/PBZ.exe` SHA-256：

```text
7b4fcd286a350780faf0824d73aa150b21cbf1bccde883e6a96386cbe09973b4
```

两版使用不同的常量文件偏移，派生密钥 SHA-256 均为 `65b75c306a77eb2df3ed5a7e6b3f8dbef360f6abefa74c465196cfa19af9637c`；工具保留两条已验证读取路径，只保存指纹，不保存密钥。每条路径仍要求目标 PBZS GCM 认证通过。小型 `PBZ.exe` 测试启动器不属于游戏主体。

基线 [samples/vanilla-base.sav](../../../samples/vanilla-base.sav) SHA-256：

```text
3782031244b8d71d94e84c18d066d6f5e84ff745c81b4e68567fc87694b3ce37
```

EXE 哈希用于离线识别精确取证对象；编辑器正常读写不计算整文件哈希。两条登记快路径验证派生指纹和目标存档的 GCM tag；不适用时按已确认的完整派生函数形状在 x64 PE 可执行节中发现引用位置，也可接受新密钥，但必须认证目标存档并验证内容。这确认读取路径对当前容器有效，不等于确认精确游戏构建。函数形状或容器格式不支持、全部候选认证失败时拒绝，不能只靠文件版本字符串、偏移处有数据或可读明文接受。

## 已纠正的高影响误判

**“改 CurrentProfileIdentifierString 就启用了方案”**：旧实现写盘及回读都成功，但真实选择仍由共享设置 `KeyBindingScheme` 控制。验收必须读取那个字段，而不是验证自己刚写的无关字段。

**“GamepadFamilyProfiles 有三条，所以是三种设备/一套共享设置”**：基线三条均为 Xbox，ProfileId 分别对应三个方案。游戏机器码先匹配 Family，再匹配 ProfileId；普通单方案编辑必须保留这一归属。

**“左键攻防”自动意味着保留右键**：保留效果取决于被覆盖的实际槽。Guard 只覆盖键鼠槽 0 时，槽 2 仍提供右键；覆盖全部右键来源则会移走右键。新增语义必须根据合并后的有效集合确保 Right+Left，手柄为 LB+X；这与闪避冲刺配方分开。

**“有 PBZS 头就应该找 Oodle 解压”**：当前容器已通过 AES-GCM 认证读写确认。旧压缩尝试不是适配其他版本时可直接继承的事实。

## 原生证据入口

详表保存在 `docs/gamepad-profile-evidence.md`，避免在技能中复制整份地址表。核心锚点均为上述构建的首选虚拟地址，ImageBase=`0x140000000`：

- `0x1466edb60`：`SetKeyBindingScheme` 路径，方案枚举经 `0x1468940a0` 转为 profile 字符串后调用引擎 profile 选择。
- `0x146884350`：手柄投影路径；实际读取 Keys 的匹配循环同时检查 Family 和 ProfileId。
- `0x146885710` / `0x1468814c0`：存储更新及清除对应记录的路径，同样保留两个匹配条件。
- `0x14688ebc0`：设备名称规范化，标准输出为 `Xbox`、`PS`、`NS`、`Other`。PS 分支选择 UTF-16 常量 `PS`，不是 `PlayStation`；`0x146882a53–0x146882a5e` 将规范化结果直接送入家族投影。
- `0x146881380`：用户设置构造路径，`0x1468813f2` 将家族存储版本初始化为 0，同时家族数组为空。版本 0 的投影分支在 `0x146884430` 重写本次目标家族的共享当前键投影，随后 `0x14688444a` 才置版本 1。

这些是静态解码证据，不是恢复的官方源代码，也不是游戏输入实测。不要把上述 VA 当作 密钥常量的 EXE 文件偏移。

离线家族构造以随程序发布的 GVAS 基线保留标签结构，以逐槽原厂表建立键值。
用户无需先连接对应手柄来制造保存记录。标准记录由 `ProfileId`、`Family`、
`Keys` 构成，Keys 的成员是 `MappingName`、`Slot`、`DefaultKey`、`Key`；
新建家族不继承另一家族的自定义键。往返与方案隔离测试可以验证工具输出，
实际硬件、Steam Input 路由和游戏使用效果仍属运行验证。

输出手柄编辑时须同时标记存储版本 1；否则游戏的版本 0 初始化分支可用共享
当前键替换新家族覆盖。这个结论来自实际调用顺序及替换目标，不能用工具
重开后仍读到相同键值来代替验证。无手柄编辑时保留原版本与原始数据。

## 后续验证怎样改变结论

版本适配先用 AssetRegistry 的类集合核对全部 InputMappingContext 和 InputAction，再解析映射的 SettingsBehavior：继承、Override、忽略分别处理。菜单数据表的显示行、资源动作名和最终可重绑 mapping name 不是同一个目录；按实际注册名称与编辑器动作全集逐项比较。固定 CommonUI、相机、菜单和 QTE 来源单独列出，不把它们当作可写 GVAS 的槽。

原生对照必须从设置对象构造函数取实际 vtable，追到 RegisterIMC 的虚槽目标。CL-302256 的新增覆写在基类注册之后把影之武装槽 2 改为槽 0 的键鼠镜像；仅比较基类机器码、资源输入或旧保存的 DefaultKey 都无法取得这个差异。默认与可独立编辑槽须分别建模，预设、恢复和有效关系不能把镜像当作额外按键来源。

读取新存档先做 byte-identical 零修改往返；失败则不支持安全编辑。单方案修改以恢复目标数据后的全文件比较检查范围，包含相同 family 的其他 ProfileId，以及同一 ProfileId 的其他 family。

PBZS 测试必须包含三个合法方案、未知值、篡改 header/nonce/tag/cipher、外部版本变化和 no-op。认证成功且其他 JSON 不变说明生成文件有效；不能代替游戏启动结果。

运行验证需明确记录游戏构建、实际选中方案、物理输入及观察结果。在确认能隔离键位、共享设置和其他本地状态前，不拿真实玩家存档做探针。单独验证“游戏 UI 展示了新绑定”“方案切换采用了对应手柄记录”“同键多动作在实际战斗中生效”，避免将其中一个当成全部成立。
